Q1: What are the two knob set generators currently supported by RapidFire AI for creating multi-config specifications?
Retrieved sources: glossary.rst, configs.rst
Answer:
RapidFire AI currently provides **two knob‑set generators** that you can use when building a multi‑config specification:

1. **`List()`** – supplies a **discrete list of values** for a knob (all values must share the same Python data type).  
2. **`Range()`** – defines a **continuous interval** (start‑to‑end) from which values are sampled, with an optional `dtype` of `"int"` or `"float"`.

These are the only knob‑set generators supported at present (see *configs.rst*).

Q2: How does RapidFire AI's adaptive execution engine differ from traditional sequential execution for multi-config experiments?
Retrieved sources: difference.rst, overview.rst, onlineagg.rst
Answer:
RapidFire AI does **not** run each configuration to completion before starting the next one.  
Instead, its **adaptive execution engine** works as follows:

1. **Shard‑based data partitioning** – the training or evaluation set is randomly split into a number of “chunks” (shards).  
2. **Interruptible, multi‑config scheduling** – all configurations are launched on **one shard at a time**; after a shard finishes, RapidFire cycles to the next shard and continues running every config in parallel on that shard.  
3. **Dynamic experiment control** – because execution is interruptible, you can **stop, resume, or clone‑modify** a running config on‑the‑fly (e.g., abort a poor‑performing config early, duplicate a promising one, change hyper‑parameters) without re‑running the whole experiment.  
4. **Online aggregation** – as each shard is processed RapidFire produces **running metric estimates with confidence intervals**, giving real‑time feedback rather than waiting for a full‑epoch or full‑eval pass.  

In contrast, **traditional sequential execution** (the status‑quo for most SFT/RFT or RAG eval pipelines) runs a single configuration **to completion** on the entire dataset before the next configuration starts. This approach is:

* **Non‑interruptible** – you must wait for the full epoch or full evaluation to finish.  
* **Single‑config at a time** – no parallelism across configs, so GPU/CPU resources are under‑utilized.  
* **No real‑time metrics** – you only see final results after the whole run, making early stopping or on‑the‑fly cloning impossible.  

Thus, RapidFire’s adaptive engine transforms multi‑config experiments from a slow, sequential batch process into a **hyper‑parallel, shard‑driven, dynamically controllable workflow** that speeds up experimentation and reduces DevOps overhead. (Source: `difference.rst`).

Q4: What is the difference between RFGridSearch and RFRandomSearch in terms of how they handle knob values?
Retrieved sources: configs.rst, experiment.rst
Answer:
**RFGridSearch vs. RFRandomSearch – how knob values are treated**

| Aspect | **RFGridSearch** | **RFRandomSearch** |
|--------|------------------|--------------------|
| **Allowed knob specifications** | • A knob may be a **single value** (e.g., `learning_rate=0.01`).<br>• Or a **`List()`** of discrete values (e.g., `batch_size=List(16, 32, 64)`).<br>• **`Range()`** is **not allowed** – using it will raise an error. | • A knob may be a **single value**, a **`List()`** of discrete values, **or** a **`Range()`** (continuous) specification (e.g., `lr=Range(0.001, 0.01, dtype="float")`). |
| **How combinations are generated** | Performs a **grid search**: every possible Cartesian‑product of the values in each `List()` is enumerated. The total number of runs equals the product of the list lengths (plus any single‑value knobs). | Performs a **random search**: for each run it **uniformly samples** one value from each knob’s set – from a `List()` (discrete uniform) or from a `Range()` (continuous uniform). Sampling is **independently‑identically‑distributed (IID)**, and the process is repeated `num_runs` times to produce distinct combinations. |
| **Key parameters controlling the process** | `configs` – must contain at least one knob expressed as a `List()`.<br>`trainer_type` – optional (e.g., `"SFT"`, `"DPO"`, `"GRPO"`). | `configs` – can contain `List()` **and/or** `Range()` knobs.<br>`num_runs` – total number of random combinations to generate.<br>`seed` – random‑seed for reproducibility (default = 42). |
| **Error behavior** | If any knob is defined with `Range()`, the call errors out. | No error; `Range()` values are sampled uniformly. |

**Summary**

- **RFGridSearch** is a deterministic grid enumerator that only works with single values or explicit lists; it cannot handle continuous ranges.  
- **RFRandomSearch** is a stochastic sampler that accepts single values, lists, **and** continuous ranges, drawing IID uniform samples for each run up to `num_runs`.

These behaviours are documented in *configs.rst* (see the “Notes” sections for each function).

Q5: How do I set up RapidFire AI for RAG evaluation on a machine without GPUs?
Retrieved sources: walkthroughrag.rst, walkthroughft.rst
Answer:
**You can run RapidFire AI’s RAG‑evaluation stack on a CPU‑only machine – you only need a Python 3.12 environment and an OpenAI API key (no GPU drivers, CUDA, or self‑hosted models are required).**  

Below is the exact sequence taken from the *walkthroughrag.rst* documentation.

---

### 1. Install the RapidFire AI package (CPU‑only)

```bash
# 1️⃣  Make sure you are on Python 3.12
python3 --version          # must show 3.12.x

# 2️⃣  Create a clean virtual‑env (optional but recommended)
python3 -m venv .venv
source .venv/bin/activate

# 3️⃣  Install the OSS package from PyPI (it pulls in all required deps)
pip install rapidfireai

# 4️⃣  Verify the installation
rapidfireai --version      # should print the current version
```

*Source:* “Step 1: Install dependencies and package” – walkthroughrag.rst (chunks 4‑5).

---

### 2. Initialise the RAG‑evaluation environment

```bash
# Install the extra libraries that RapidFire uses for RAG evals
rapidfireai init --evals
```

- Run this **once per virtual‑env** (or when you change GPU hardware).  
- No GPU is needed; the command will only pull CPU‑compatible packages.

*Source:* “initialize rapidfireai to use the correct dependencies for RAG evals” – walkthroughrag.rst (chunk 11).

---

### 3. Provide an OpenAI API key

Since you are not using any self‑hosted embedding or generation models, RapidFire will call the OpenAI services for both embeddings and LLM generation. Supply the key via a config argument (the same way the GSM8K and SciFact tutorial notebooks do):

```python
from rapidfireai import RapidFireConfig

cfg = RapidFireConfig(
    openai_api_key="sk-XXXXXXXXXXXXXXXXXXXXXXXX"
)
```

*Source:* “you must provide a valid OpenAI API key via a config argument as shown in the GSM8K and SciFact tutorial notebooks” – walkthroughrag.rst (chunks 3‑4‑5).

---

### 4. Start the services (frontend + API)

```bash
rapidfireai start
```

You should see output similar to:

```
... RapidFire Frontend is ready
Open your browser and navigate to: http://0.0.0.0:8853
```

Open the URL in a local browser; the dashboard will be fully functional even though the machine has no GPU.

*Source:* “Next start RapidFire AI services… rapidfireai start” – walkthroughrag.rst (chunk 11).

---

### 5. (Optional) Use Google Colab for a quick try‑out

If you just want to experiment without any local install, the documentation also offers a pre‑configured Colab notebook:

```
https://tinyurl.com/rapidfireai-rag-colab
```

*Note:* Colab is limited to small models and datasets because it runs on free resources.

*Source:* “Google Colab – Try RapidFire AI RAG instantly in your browser” – walkthroughrag.rst (chunks 2‑3‑4).
