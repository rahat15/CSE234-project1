# RAG Pipeline and Context Engineering Report

## 1. Data Creation Methodology

We created a custom golden evaluation set of 20 question-answer pairs over the RapidFire AI OSS documentation corpus. The goal was not to create shallow lookup questions, but to test whether a RAG system could retrieve the right documentation fragments and synthesize technically correct answers under a fixed context budget. Each question was written against one or more `.rst` source files and paired with explicit source evidence spans in the form of file names and line ranges.

The questions were designed to cover several types of documentation use cases. Factual questions asked for concrete parameters, supported features, or API behavior. Conceptual questions asked why a design choice matters, such as why online aggregation can make config comparisons more reliable than downsampled batch evaluation. Procedural questions asked how to set up or operate RapidFire AI in realistic conditions, for example running RAG evaluation on CPU-only machines. Comparative questions asked the system to distinguish related mechanisms such as `RFGridSearch` versus `RFRandomSearch`, or CPU versus GPU retrieval paths. We also included multi-hop questions whose evidence came from more than one document, forcing the retriever to connect related sections instead of relying on a single obvious paragraph.

Ambiguity was reduced in two ways. First, each question was scoped to information that was explicitly answerable from the corpus. We avoided questions that required outside knowledge, subjective judgment, or inference beyond the documentation. Second, reference answers were written to include the level of detail expected from the evidence spans, neither merely naming a concept nor adding unsupported implementation claims. This was important because an answer can appear plausible while still failing faithfulness if it fills gaps from general LLM knowledge.

Evidence spans were selected manually from the source documentation. For each question, we identified the smallest set of files and line ranges needed to support the reference answer. When a question required more than one concept, we included multiple source evidence entries rather than expanding a single span until it became noisy. This helped keep the evaluation aligned with realistic RAG behavior: good systems should retrieve enough context to answer completely, but not so much that unrelated documentation pollutes the prompt.

The final golden set intentionally avoids trivial API lookup questions such as “what is the name of this class?” unless the answer required some interpretation of usage or constraints. The set balances retrieval difficulty across direct, neighboring, and multi-document evidence. It also includes hidden-metric-inspired checks: whether the answer is faithful to retrieved text, whether it is complete enough to satisfy a graduate-level technical question, and whether it remains concise. We iteratively refined questions whose initial wording was too broad, whose answer could be guessed without retrieval, or whose evidence span was too diffuse.

## 2. Final Pipeline Architecture

The final system is a retrieval-augmented generation pipeline over the RapidFire documentation corpus in `data/sourcedocs`. The submitted entry point is `main.py`, which accepts an input JSON file containing `question_id` and `question`, retrieves evidence from the documentation, sends the assembled context to a Triton OpenAI-compatible chat model, and writes the required output fields: `question_id`, `answer`, `retrieved_context`, and `sources`.

Although we initially experimented with conventional dense RAG components, the final selected retriever uses a sparse TF-IDF representation over character n-grams rather than a dense embedding model. Specifically, the best configuration uses `char_wb` n-grams of length 3 to 5 over word-boundary character windows. This choice worked well for the documentation corpus because many relevant terms are API identifiers, class names, configuration names, and file-specific phrases. Dense semantic embeddings can smooth over these lexical details, while character n-grams preserve partial matches such as `RFGridSearch`, `RFRandomSearch`, `RFLangChainRagSpec`, and parameter names. In this setting, exact and near-exact lexical matching was more valuable than broad semantic similarity.

The “vector store” for the final pipeline is an in-memory sparse TF-IDF matrix, queried with cosine similarity. We did not use FAISS in the final selected pipeline because the corpus is small enough that sparse matrix search is fast and deterministic. Earlier RapidFire notebook variants used the standard RAG pattern of embedding models, FAISS vector stores, similarity/MMR retrieval, and cross-encoder reranking. Those experiments were useful baselines, but they introduced more moving parts than the corpus required. The final pipeline favors reproducibility and source-sensitive retrieval over architectural complexity.

Chunking was the most important design decision. The final configuration uses 128-word chunks with 96-word overlap. This relatively small chunk size keeps each retrieved unit focused, while the large overlap prevents important API descriptions from being split across chunk boundaries. The overlap is intentionally aggressive because documentation often defines a concept in one sentence and states constraints or examples in the neighboring sentences. Without overlap, retrieval could return a chunk containing a class name but miss the conditions needed for a faithful answer.

For each query, the retriever scores all chunks and considers the top 25 candidate chunks. It then serializes up to 7 context chunks, deduplicating source files where possible while still preserving high-scoring repeated evidence when needed. The output `sources` field is constructed from the selected chunks using file names and approximate line spans. We did not apply a separate cross-encoder reranker in the final pipeline. The main reason is that reranking added latency and, in early experiments, did not reliably improve the final judged score on this small documentation set. The character n-gram retriever already produced high recall, and the remaining failures were more often due to answer synthesis or evidence ambiguity than candidate ordering alone.

Context serialization is deliberately simple. Each retrieved chunk is prefixed with its source file and chunk id, then separated by clear delimiters. This gives the generator enough provenance to cite relevant files in prose and reduces the chance that adjacent chunks are interpreted as one continuous passage. The prompt instructs the model to answer only from retrieved evidence, be complete but concise, and state when evidence is insufficient. The generation model is `api-gpt-oss-120b` through Triton’s OpenAI-compatible API, with temperature set to zero and `max_completion_tokens` set to 1024.

The project imposed a 2000-token context budget per query. To avoid overflow, the code applies a context budget cap before generation. Token counting is approximated conservatively by word count, and context chunks are added in ranked order until the limit would be exceeded. In the final validation run, the maximum retrieved context length was 937 words, leaving margin for the question and instructions. This budget discipline mattered: retrieval quality alone is not sufficient if the prompt becomes overloaded with loosely related text. The final design prioritizes high-density evidence over maximizing raw retrieval depth.

## 3. Experimentation Methodology

We used RapidFire AI to structure and compare multiple RAG configurations over the validation set. The experiments were organized as a grid over discrete retrieval and generation knobs. A grid search was appropriate because the search space was small, interpretable, and dominated by a few engineering choices: chunk size, overlap, analyzer type, n-gram range, retrieval depth, and generation token budget. We did not rely on random search for the final reported sweep because random sampling would make it harder to isolate the effect of individual retrieval design choices.

RapidFire was useful because it gave a consistent interface for running multiple configurations, collecting per-run metrics, and comparing results in a single experiment log. The notebook `discussion1-rag-scifact.ipynb` was adapted from the SciFact tutorial to the uploaded RapidFire documentation corpus. Each run processed the same 45-question validation set, used the same Triton generation model, and was evaluated with the same retrieval and generation metrics. This kept comparisons focused on configuration changes rather than data or model drift.

The main sweep varied chunking and retrieval representation. Word-based TF-IDF configurations tested whether documentation concepts were better captured by normal token sequences. Character n-gram configurations tested whether API names, abbreviations, and parameter strings were more important. Overlap was varied because overlap controls the boundary failure rate: too little overlap loses definitions split across chunks, while too much overlap increases redundancy and can reduce context diversity. We also tested two completion-token limits to see whether longer answer budgets improved generation quality or simply increased verbosity.

We also considered standard dense RAG knobs from the RapidFire tutorial workflow: embedding model, FAISS vector store, similarity versus MMR retrieval, retrieval `k`, reranker choice, and reranker `top_n`. In the earlier notebook adaptation, these components helped establish a baseline and clarified the tradeoff between recall and context noise. Similarity retrieval tended to rank obvious lexical matches high, while MMR was more useful when questions required coverage across multiple sections. However, MMR could also reduce precision when it diversified into adjacent but non-answer-bearing documentation. Cross-encoder reranking was attractive in principle, but for this corpus the cost and complexity were not justified by the observed gains compared with the simpler sparse approach.

The evaluation workflow had two layers. During rapid iteration, we used retrieval metrics and a lexical generation overlap metric because they were cheap and stable enough for comparing many configurations. After selecting the strongest retrieval setup, we ran a slower LLM-based judge over the best output. This judge evaluated correctness, faithfulness, and completeness against the golden answers and source evidence. Separating fast proxy evaluation from slower final judging was important: the proxy was useful for engineering iteration, but it was not treated as the final measure of answer quality.

## 4. Results and Analysis

The final selected configuration was `char_128_96` with the `api-gpt-oss-120b` generator and a 1024-token completion budget. On the 45-question validation set, it achieved Precision@5 of 0.5019, Recall@5 of 0.9556, F1@5 of 0.6311, and a retrieval score of 0.6962. The LLM judge reported correctness of 0.8667, faithfulness of 0.9111, completeness of 4.13 out of 5, and a normalized partial generation score of 0.8681. The resulting partial total score was 0.7822.

The strongest observation from the sweep is that recall mattered more than precision for this task, but only up to the point where context remained dense. The final configuration had lower MRR than some word-based configurations, but much higher recall. This means the first retrieved file was not always the single best file, yet the relevant evidence usually appeared somewhere in the top five. For multi-hop documentation questions, that behavior was beneficial: the generator needed several relevant pieces rather than one perfectly ranked snippet.

Character n-gram retrieval outperformed the best word-based retrieval score because the corpus contains many technical identifiers. Word tokenization treats names such as `RFLangChainRagSpec`, `RFGridSearch`, and `enable_gpu_search` as brittle tokens. Character n-grams preserve useful substrings and make retrieval more tolerant to slight wording differences between the user question and documentation. This improved source recall, especially for questions about configuration objects, class names, and API options.

Chunk size and overlap showed a clear tradeoff. Larger chunks such as 192 words often produced fluent answers because they supplied broader local context, and run 1 had the highest MRR among the reported configurations. However, larger chunks also carried more unrelated text into the prompt. This can make the generator include plausible but unsupported details, especially when neighboring documentation sections discuss related features. Smaller chunks improved focus, but without enough overlap they risked separating a concept from its constraints. The final 128/96 setting was a good compromise: chunks were short enough to be specific, but overlap was high enough to preserve local continuity.

The lexical generation overlap metric did not perfectly predict the final judged result. For example, word-based configurations had slightly higher overlap scores in some runs, but worse retrieval scores. This is expected because lexical overlap rewards surface similarity to reference answers, while judged correctness and faithfulness depend on whether the generated answer is supported by the retrieved context. A model can produce an answer that overlaps the reference but misses a constraint, or it can use different wording while still being correct. For that reason, we used the overlap metric as an iteration signal rather than a final claim about answer quality.

Increasing the completion budget from 1024 to 1536 tokens produced only a small improvement in lexical generation overlap for the same retrieval setup (`word_192_16`) and did not address the underlying retrieval limitation. This suggests that the bottleneck was not answer length. Once the relevant evidence is absent or diluted, allowing the generator to write more does not reliably improve correctness. In fact, longer outputs can increase hallucination risk if the prompt contains partially relevant context and the model tries to infer missing details.

The main failure cases fell into three categories. First, some retrieval failures occurred when the question used conceptual phrasing but the documentation expressed the answer through concrete API examples. Second, context pollution occurred when high-scoring chunks came from related tutorial pages but did not contain the exact constraint being asked about. Third, generation failures occurred even when source files were retrieved, usually because the model gave a broad answer and omitted a specific condition required by the reference. These failures explain why faithfulness was high but not perfect, and why completeness was strong but still below the maximum.

Reranking and retrieval depth had mixed effects. Increasing depth improved the chance of including all evidence for multi-hop questions, but it also increased the amount of context the generator had to filter. Under a 2000-token budget, retrieval depth is not free: every additional chunk consumes space that could have been used for a more precise span. A reranker can help if it reliably promotes answer-bearing chunks, but when the initial retriever already returns many near-duplicate documentation snippets, reranking mostly reorders similar evidence rather than removing noise. In future work, we would explore a hybrid sparse+dense retriever followed by a lightweight reranker trained or calibrated for documentation QA, rather than applying a generic reranker blindly.

The final pipeline was selected because it had the best retrieval score and the best final judged score, not because it was the most complex architecture. Its strength is that it matches the structure of the corpus: technical documentation with many named APIs, short sections, and line-grounded evidence. With more time, we would improve the system in three directions. First, we would implement section-aware chunking based on `.rst` headings instead of fixed word windows. Second, we would add query expansion for aliases and API names, which may improve conceptual questions without increasing context size. Third, we would evaluate a hybrid retriever that combines sparse character n-grams with dense embeddings, using reranking only after candidate generation has sufficient recall.

## 5. AI Tools Statement

AI tools were used during development as engineering assistants, not as a replacement for implementation or evaluation. ChatGPT/Codex helped with debugging notebook code, adapting the SciFact tutorial workflow to the uploaded documentation corpus, writing utility scripts, summarizing experiment outputs, and drafting report language. LLM-based tools were also useful for identifying likely failure modes and for making the final report more concise and coherent.

All generated code and report content was reviewed and validated by the students. The submitted pipeline was executed locally, output JSON files were checked for the required schema, context lengths were verified against the 2000-token budget, and configuration results were collected from RapidFire experiment logs. Design decisions such as the final retrieval configuration, context assembly strategy, and use of Triton GPT were made based on observed metrics and manual inspection of outputs, not simply accepted from AI suggestions.

AI assistance was also used to accelerate documentation understanding and to brainstorm evaluation questions. However, golden QA pairs were grounded in the source documentation with explicit file and line evidence, and answers were checked for answerability from the corpus. The final submission reflects an iterative engineering process: building a working RAG system, testing multiple configurations, comparing retrieval and generation metrics, and selecting the pipeline that best satisfied the project constraints.
